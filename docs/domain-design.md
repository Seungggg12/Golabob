# 골라밥 도메인 설계

## 1. 설계 원칙

- 인증 역할과 실제 사업자 승인 상태를 분리한다.
- 모든 쓰기 작업은 현재 사용자와 리소스 소유권을 함께 검증한다.
- 상태 전이는 서비스 메서드가 아닌 도메인 규칙으로 명시한다.
- 오퍼 선택은 요청·오퍼·예약을 묶는 단일 트랜잭션으로 처리한다.
- 현재 API 응답 형식은 불가피한 버전 변경 전까지 유지한다.
- 데이터베이스 제약조건을 애플리케이션 검증의 최종 안전장치로 사용한다.

## 2. 핵심 도메인

| 도메인 | 책임 | 주요 불변 조건 |
| --- | --- | --- |
| User | 계정, 로그인 식별자, 계정 상태 관리 | 이메일은 유일하고 정지 계정은 인증할 수 없다 |
| UserRole | 계정이 수행할 수 있는 역할 관리 | 모든 계정은 `user`를 가지며 승인된 계정만 `owner`를 가진다 |
| OwnerApplication | 사업자 신청과 관리자 심사 관리 | 승인 시 한 번만 owner 역할을 부여한다 |
| Restaurant | 식당 정보와 운영 승인 상태 관리 | 대표 owner는 한 명이며 승인된 식당만 오퍼를 보낼 수 있다 |
| DiningRequest | 사용자의 회식 조건과 모집 상태 관리 | 한 사용자 소유이며 마감 후 오퍼를 받을 수 없다 |
| Offer | 식당이 제안한 가격과 조건 관리 | 한 식당은 한 요청에 유효 오퍼 하나만 보낼 수 있다 |
| Reservation | 선택 오퍼 예약과 일반 식당 예약 관리 | 예약 유형에 맞는 참조만 가지며 중복 예약을 방지한다 |
| Review | 완료 예약에 대한 사용자 평가 관리 | 예약자만 예약당 리뷰 하나를 작성할 수 있다 |
| WaitingSetting | 식당별 원격 웨이팅 접수 정책 관리 | 승인 식당 owner만 접수 상태와 호출 제한 시간을 변경한다 |
| WaitlistEntry | 사용자 대기 등록과 호출·착석 상태 관리 | 사용자는 식당별 활성 웨이팅을 하나만 가진다 |
| StatusHistory | 주요 상태 변경의 수행 주체·사유 기록 | 상태가 바뀌는 트랜잭션 안에서 함께 기록한다 |

## 3. 계정과 역할

### User

- 회원가입 시 기본 역할은 항상 `user`다.
- `users.status`는 `active`, `suspended`, `withdrawn`을 사용한다.
- 로그인 시 계정 상태를 확인하고 `active`가 아니면 토큰을 발급하지 않는다.
- `users.role`은 기존 코드 호환을 위한 대표 역할로만 유지하고 권한 판단은 `user_roles`를 기준으로 한다.

### OwnerApplication

- 사용자는 사업자 정보와 증빙 자료를 제출한다.
- 상태는 `pending`, `approved`, `rejected`, `withdrawn`을 사용한다.
- 관리자가 승인하면 신청 상태 변경과 `user_roles.owner` 추가를 한 트랜잭션으로 처리한다.
- 사업자등록번호는 화면과 로그에서 마스킹하고 운영 환경에서는 암호화 저장을 적용한다.

## 4. 식당

- 식당은 대표 owner 한 명을 `owner_id`로 참조한다.
- owner 한 명은 여러 식당을 등록할 수 있다.
- 식당 등록 직후 상태는 `pending`이며 관리자 승인 후 `approved`가 된다.
- `rejected` 식당은 수정 후 재심사를 요청할 수 있고 `suspended` 식당은 신규 오퍼를 보낼 수 없다.
- 영업시간, 편의시설, 사진은 검색과 정렬을 위해 별도 테이블로 관리한다.

## 5. 회식 요청

- 생성 시 상태는 `open`이며 `offer_deadline_at`을 반드시 가진다.
- `open`이고 유효한 오퍼가 없을 때만 조건을 수정할 수 있다.
- 사용자는 본인 요청만 상세 조회·수정·취소할 수 있다.
- 사장님은 `open`이고 마감되지 않은 요청만 조회할 수 있다.
- 요청 마감 또는 회식 시작 시각이 지나면 `expired` 처리한다.

## 6. 오퍼

- 사장님은 본인이 소유한 `approved` 식당으로만 오퍼를 작성할 수 있다.
- 같은 식당은 같은 요청에 유효 오퍼를 하나만 가질 수 있다.
- `pending`이고 요청이 `open`일 때만 수정·취소할 수 있다.
- 오퍼 만료 시각은 요청 마감 시각을 넘을 수 없다.
- 선택된 오퍼는 `selected`, 나머지 `pending` 오퍼는 `rejected`로 변경한다.

## 7. 예약

- 예약 유형은 역제안 예약 `offer`와 일반 예약 `direct`를 사용한다.
- 역제안 예약은 `dining_request_id`와 `accepted_offer_id`를 필수로 참조하고 일반 예약에서는 두 값을 비워 둔다.
- 일반 예약은 사용자가 승인된 식당을 선택하고 수용 인원·예약 시각을 검증한 뒤 생성한다.
- 예약 가격, 인원, 날짜, 시간, 메뉴 요약은 확정 시점 값을 저장해 이후 원본 수정의 영향을 받지 않게 한다.
- 사용자와 사장님 모두 예약 시작 전 취소할 수 있으며 취소 사유는 필수다.
- 취소 수수료와 결제는 MVP 범위에서 제외한다.

## 8. 주요 트랜잭션 경계

### 원격 웨이팅 등록

1. 식당 웨이팅 설정 행을 잠근다.
2. 승인 식당이며 접수 중인지, 인원이 허용 범위인지 확인한다.
3. 같은 사용자의 해당 식당 활성 웨이팅이 없는지 확인한다.
4. 영업일 기준 다음 대기 번호를 원자적으로 발급한다.
5. `waiting` 상태 웨이팅과 상태 이력을 생성한다.

### 웨이팅 호출과 착석

- 사장님은 본인 식당의 가장 앞선 `waiting` 항목을 `called`로 변경한다.
- 호출 시 `called_at`과 `expires_at`을 기록한다.
- 제한 시간 안에 입장하면 `seated`, 사용자가 취소하면 `canceled`, 제한 시간을 넘기면 `no_show`로 변경한다.
- 순서를 건너뛴 호출은 사유를 필수로 기록한다.

### 사업자 승인

1. 신청 행을 잠근다.
2. 신청이 `pending`인지 확인한다.
3. 신청을 `approved`로 변경한다.
4. `user_roles`에 `owner`를 추가한다.
5. 승인 이력을 기록한다.

### 오퍼 선택과 예약 확정

1. 회식 요청 행을 `FOR UPDATE`로 잠근다.
2. 요청 소유자와 `open` 상태를 확인한다.
3. 선택 오퍼가 요청에 속하고 `pending`이며 만료되지 않았는지 확인한다.
4. 선택 오퍼를 `selected`로 변경한다.
5. 나머지 `pending` 오퍼를 `rejected`로 변경한다.
6. 요청을 `matched`로 변경한다.
7. 예약을 생성한다.
8. 요청·오퍼·예약 상태 이력을 기록한다.

`reservations.dining_request_id`와 `reservations.accepted_offer_id`의 유일 제약으로 중복 예약을 최종 차단한다.

### 일반 예약 확정

1. 승인된 식당과 대표 owner를 확인한다.
2. 예약 시각과 인원이 식당 운영 조건에 맞는지 검증한다.
3. 같은 식당·시간대의 예약 충돌 여부를 잠금 또는 수용량 정책으로 확인한다.
4. `direct` 유형 예약을 생성한다.
5. 예약 상태 이력을 기록한다.

## 9. 권한 규칙

| 작업 | user | owner | admin |
| --- | --- | --- | --- |
| 회식 요청 등록·내 요청 관리 | 허용 | user 역할로 허용 | 운영 조회만 허용 |
| 모집 요청 조회 | 본인 요청만 | 허용 | 허용 |
| 오퍼 작성·관리 | 불가 | 승인된 본인 식당만 허용 | 운영 조회만 허용 |
| 오퍼 선택 | 요청 소유자만 허용 | 불가 | 분쟁 처리 경로에서만 허용 |
| 예약 조회·취소 | 예약자 본인만 허용 | 본인 식당 예약만 허용 | 허용 |
| 웨이팅 등록·내 상태 조회 | 허용 | user 역할로 허용 | 운영 조회만 허용 |
| 웨이팅 접수·호출·착석 관리 | 불가 | 본인 식당만 허용 | 허용 |
| 사업자·식당 승인 | 불가 | 불가 | 허용 |

## 10. 구현 시 지켜야 할 규칙

- 컨트롤러는 인증 사용자와 DTO만 서비스에 전달한다.
- 서비스는 역할, 소유권, 현재 상태, 마감 시각 순서로 검증한다.
- 상태 변경 SQL은 영향받은 행 수를 확인하고 0이면 충돌로 처리한다.
- 중복 요청에 대비해 예약 확정 API는 `Idempotency-Key`를 지원한다.
- 비밀번호, 토큰, 사업자번호 원문, 취소 사유 전문을 애플리케이션 로그에 남기지 않는다.
